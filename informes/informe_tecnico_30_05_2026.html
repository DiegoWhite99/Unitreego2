1 · Resumen ejecutivo

El objetivo de la sesión fue atacar la queja principal: "a veces la app se queda colgada o no funciona". 2 · Diagnóstico — por qué la app se colgaba

El backend tiene un único event loop de asyncio corriendo en un hilo dedicado (core/runtime.py). Ese loop es el que hace todo lo asíncrono:

  • Recibe el video WebRTC del Go2 (cada frame que va a YOLO).
  • Envía todos los comandos al robot (Move, poses, SPORT_CMD).
  • Procesa las suscripciones del lidar (pose + nube de puntos).
  • Corre los loops de Auto-Ruta y Follow-QR.
La regla de oro: si cualquier cosa bloquea ese hilo (una llamada de red lenta, un cálculo pesado), se congela simultáneamente el video, los comandos y los sensores → la app "se cuelga". El problema #2 violaba exactamente esta regla.

3 · Arreglo 1 · Cambiar la IP destruía la configuración

El endpoint POST /api/config/ip guardaba la IP nueva sobrescribiendo todo el archivo config/config.py, dejándolo con una sola línea.

Antes

with open(config_path, "w") as f:
    f.write(f'ROBOT_IP = "{new_ip}"\n')

Esto borraba: carga del .env, la clave AES, los modelos del agente y las API keys. Tras un solo cambio de IP, el agente y la conexión dejaban de funcionar.

Después

_upsert_env_var("ROBOT_IP", new_ip)
os.environ["ROBOT_IP"] = new_ip
robot_state["ip"] = new_ip

Ahora la IP se persiste en el .env (de donde config.py ya la lee) con un upsert que preserva el resto del archivo. config.py no se toca nunca.

Archivo: api/connection.py. Se añadió la función _upsert_env_var() con validación básica del formato de IP/host.

4 · Arreglo 2 · El cuelgue principal — IA bloqueando el event loop

Durante la Auto-Ruta, cuando el "asistente IA de trayectoria" está activo, el robot consulta a un modelo (OpenAI/Gemini) para corregir el desvío lateral. El problema: esa consulta de red se hacía de forma síncrona dentro del loop de control, en core/autoroute.py · _follow_segment().

Cada corrección (hasta una vez por segundo cuando hay desvío) congelaba el event loop 1–3 segundos esperando la respuesta del modelo. Durante esos segundos: el video se traba, los comandos Move no salen y el robot "se cuelga". Esta era casi con seguridad la causa que percibías en las pruebas de patrullaje e IA.

Antes — bloqueante

adj = _ai_path_adjustment(payload)  # ← espera
                                    #   la red AQUÍ,
                                    #   congela TODO
ai_cached = clamp(adj)

Después — fire-and-forget en thread

# lanza en un hilo aparte, NO espera
ai_future = loop.run_in_executor(
    None, _ai_path_adjustment, payload)
# en otra iteración, cuando ya está listo:
if ai_future.done():
    ai_cached = _apply_ai_adjustment(
        ai_future.result(), ai_cached)

La consulta a la IA ahora corre en un hilo del executor, en paralelo. El loop de control sigue enviando comandos a su ritmo de ~7 Hz sin pausarse jamás, y aplica la corrección de la IA cuando esta llega (un par de iteraciones después). Si la IA falla o tarda, el control sigue con el último valor cacheado (degradación suave). Se añadió el helper _apply_ai_adjustment() que acota los valores recibidos a rangos seguros.

Nota: las llamadas de IA del chat del agente Diver (core/agents/chat.py) no tenían este problema: corren en el hilo de la petición HTTP, no en el event loop. Por eso no se tocaron.

5 · Arreglo 3 · Lag al conducir (move/stop)

Los comandos del joystick por Socket.IO (move_command) usaban run_async(), que bloquea el hilo hasta que el comando se envía (con timeout de 30 s). Con el joystick a alta frecuencia, esto añadía latencia y —peor— un stop podía quedar atascado detrás de un move en cola, retrasando el frenado.

Antes

run_async(robot_send_command("Move", …))
# espera el envío → bloquea el hilo

Después

run_async_no_wait(robot_send_command(…))
# encola y sigue → hilo libre al instante

Archivo: api/sockets.py. Ahora move y stop se encolan sin esperar; se ejecutan en orden y el stop ya no queda atrapado.

6 · Arreglo 4 · Arranque frágil del servidor

El arranque (app.py) usaba debug=True, lo que activaba el reloader de Flask. Dos consecuencias malas para un robot:

  • Al guardar cualquier archivo, el servidor se reiniciaba → se perdía la conexión al robot a mitad de operación.
  • El reloader duplica el proceso: doble event loop asyncio y doble carga del modelo YOLO.
  • Si se lanzaba sin terminal (doble-clic / pythonw / servicio), Flask-SocketIO lanzaba un RuntimeError y no arrancaba.
debug = os.environ.get("FLASK_DEBUG", "0") in ("1","true","yes","on")
socketio.run(app, host="0.0.0.0", port=5000,
             debug=debug,
             use_reloader=False,          # sin reinicios a mitad de operación
             allow_unsafe_werkzeug=True)  # arranca aunque no haya terminal

Ahora debug está apagado por defecto (se activa con la variable de entorno FLASK_DEBUG=1 solo si hace falta depurar).

7 · Arreglo 5 · Dependencias faltantes

El código usaba paquetes que no estaban declarados en requirements.txt. En otro equipo, instalar con pip install -r requirements.txt dejaba el agente o el arranque a medias.

Añadidos: google-generativeai (fallback Gemini del agente), python-dotenv (carga del .env), simple-websocket (transporte WebSocket de Socket.IO) y python-socketio.
