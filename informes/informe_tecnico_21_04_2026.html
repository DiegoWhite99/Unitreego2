1. Refactor del Modo Force — Sostenido, Movil y Fallback

1.1 Problema Identificado

En entornos con muchas detecciones del lidar (habitaciones con mobiliario denso, pasillos con sillas, etc.), el sensor de proximidad disparaba alertas con alta frecuencia y el unico mecanismo previo para saltarse el bloqueo era un doble-tap WASD que se desactivaba en cuanto el operador soltaba todas las teclas. El resultado: el operador terminaba tecleando en ciclo tap–tap–mover–soltar–repetir para cada tramo, lo que degrada la ergonomia y la reaccion a tiempo en operacion real.

1.2 Rediseno — Tres Fuentes, Un Estado

Se reemplazo el boolean forceActive unico por un estado multi-fuente. Tres flags independientes se unifican con un OR logico en el helper refreshForceState(), que tambien gestiona la visibilidad del badge FORCE en la UI:

FUENTE 1 — Shift sostenido (escritorio)
keydown/keyup sobre 'Shift' → forceShift = true/false
FUENTE 2 — Boton Override (movil)
pointerdown/up/cancel/leave sobre #cr-mobile-override → forceButton
FUENTE 3 — Doble-tap WASD (fallback)
Dos pulsaciones de la misma tecla en <350 ms → forceDoubleTap, limpiado en stopLoop
↓  refreshForceState()  ↓
SALIDA — forceActive
forceActive = forceShift || forceButton || forceDoubleTap
Cada tick de movimiento agrega force: true al move_command si activo. 
// website/js/controlRemoto.js
refreshForceState() {
    const m = this.movement;
    const active = m.forceShift || m.forceButton || m.forceDoubleTap;
    m.forceActive = active;
    if (active) this.showForceBadge();
    else this.hideForceBadge();
},

// En startLoopIfNeeded(), cada 200 ms:
const payload = { ...v };
if (this.movement.forceActive) payload.force = true;
this.socket.emit('move_command', payload);

1.3 Boton Forzar en Movil (Override Hold)

Se agrego a la barra de acciones movil un nuevo boton en color ambar que actua como hold-to-press. A diferencia de las acciones puntuales (saludar, sentarse, recuperarse) que responden a click, este boton responde a los eventos de puntero de bajo nivel para poder distinguir presion sostenida de toque simple. 

// setupMobileOverride() en controlRemoto.js
const press = (e) => {
    if (e) e.preventDefault();
    if (this.movement.forceButton) return;
    this.movement.forceButton = true;
    btn.classList.add('pressed');
    btn.setAttribute('aria-pressed', 'true');
    this.refreshForceState();
};
const release = () => {
    if (!this.movement.forceButton) return;
    this.movement.forceButton = false;
    btn.classList.remove('pressed');
    btn.setAttribute('aria-pressed', 'false');
    this.refreshForceState();
};

btn.addEventListener('pointerdown',   press);
btn.addEventListener('pointerup',     release);
btn.addEventListener('pointercancel', release);
btn.addEventListener('pointerleave',  release);
Decision de diseno. Los listeners cubren pointerup, pointercancel y pointerleave: si el operador desliza el dedo fuera del boton sin levantarlo, el override tambien se libera. Esto evita estados colgados donde el boton visualmente se ve pulsado pero el sistema ya no recibe eventos.

1.4 Silenciamiento del Handler de Alertas en Frontend

El handler onProximityAlert hacia stopMovement() sin condicion, lo que anulaba el force al primer tick del sensor porque reseteaba el estado del teclado. Ahora el handler retorna de inmediato si forceActive es true: 

onProximityAlert(data) {
    // Modo FORCE (Shift, Override o doble tap): el operador acepto el riesgo.
    // Ignoramos la alerta completa: nada de stopMovement, ni stop_command,
    // ni banner. El robot sigue caminando como si el sensor estuviera apagado.
    if (this.movement.forceActive) return;

    // ... flujo normal: dedup TTS, stopMovement, emit('stop_command'), banner
}

1.5 Ventana de Gracia en Backend — _force_until

En el backend se agrego un campo _force_until al diccionario proximity_sensor. Cada move_command con force=true renueva la ventana a time.time() + 0.8. El trigger de alertas de proximidad consulta esta marca como primer filtro: si la ventana esta abierta, el trigger descarta la alerta sin emitir, sin flipear _alert_active y sin publicar Move=0. 

# app.py — _trigger_proximity_alert()
def _trigger_proximity_alert(distance_m, direction, source):
    # Si la ventana de FORCE esta abierta, descartamos todo: el operador
    # pidio explicitamente caminar normal pese al obstaculo.
    if time.time() < proximity_sensor.get("_force_until", 0.0):
        return

    if proximity_sensor["_alert_active"]:
        return

    proximity_sensor["_alert_active"] = True
    socketio.emit("proximity_alert", { ... })
    run_async_no_wait(robot_send_command("Move", {"x": 0.0, "y": 0.0, "z": 0.0}))

1.6 Cierre Inmediato al Soltar

Version iniciaol dejaba 0.8 s de inercia tras soltar la combinacion, pero el operador pidio que el sensor volviera a proteger de inmediato. Ahora, cualquier move_command sin force=true y cualquier stop_command cierran la ventana explicitamente: 

# app.py — handle_move_command()
if force:
    proximity_sensor["_force_until"] = time.time() + 0.8
    if proximity_sensor["_alert_active"]:
        proximity_sensor["_alert_active"] = False
        proximity_sensor["_clear_since"] = 0.0
else:
    # Operador solto: cerramos la ventana en seco para que el sensor proteja.
    proximity_sensor["_force_until"] = 0.0

# app.py — handle_stop_command()
proximity_sensor["_force_until"] = 0.0
proximity_sensor["_last_cmd_x"] = 0.0

2. Mapa de Calor 2.5D del Entorno

2.1 Persistencia del Heatmap entre Paginas

Antes, al guardar una ruta en el Control Remoto, solo se serializaban los waypoints y la distancia recorrida. La Auto-Ruta leia esa ruta y la dibujaba sobre un canvas vacio, perdiendo todo el contexto visual que el operador habia construido al caminar el entorno. Ahora el heatmap (grid de densidad derivado del lidar L1) tambien se persiste: 

// controlRemoto.js — setupSaveRoute()
const heatArr = [];
for (const [k, v] of this.trace.heat) {
    const [ix, iy] = k.split(',').map(Number);
    heatArr.push([ix, iy, v]);
}
localStorage.setItem('daiver:lastRoute', JSON.stringify({
    savedAt: Date.now(),
    points: sampled,
    totalMeters: this.trace.totalMeters,
    heatCellSize: this.trace.heatCellSize,
    heat: heatArr,
}));

2.2 Proyeccion 2.5D (Cavalier Simplificado)

La Auto-Ruta renderiza el mundo XY proyectandolo sobre la pantalla con compresion en Y (foreshortening). Las constantes TILT_KY y COLUMN_HEIGHT_PX gobiernan la inclinacion y la altura maxima de las columnas de heatmap. La transformacion es afin y admite inversa exacta, lo cual es esencial porque el editor de waypoints necesita convertir clicks de pantalla a coordenadas de mundo. 

const TILT_KY = 0.62;
const COLUMN_HEIGHT_PX = 28;

worldToScreen(x, y) {
    return [
        this.view.originX + x * this.view.scale,
        this.view.originY - y * this.view.scale * TILT_KY,
    ];
},

screenToWorld(sx, sy) {
    return [
        (sx - this.view.originX) / this.view.scale,
        (this.view.originY - sy) / (this.view.scale * TILT_KY),
    ];
},

2.3 Render de Columnas con Volumen

Cada celda activa del heatmap se dibuja como una columna vertical cuya altura es proporcional a la intensidad acumulada (cantidad de veces que el lidar vio esa celda). Para dar impresion de volumen real (y no un parche plano), cada columna compone cuatro elementos:

  1. Sombra eliptica en el suelo (opacidad proporcional a intensidad), siempre tras la celda.
  2. Cara frontal con un linearGradient vertical: color mas saturado arriba, oscurecido abajo (simula iluminacion cenital).
  3. Cara superior como paralelogramo con desplazamiento en Y proporcional a cellPxYGround * 0.35, color mas brillante y alpha mayor (vista isometrica).
  4. Arista luminosa amarillenta en el borde superior para dar hot rim y separacion visual entre columnas contiguas.

El color del gradiente va de azul profundo (intensidad baja) a rojo anaranjado (intensidad alta), reforzando el codigo visual “mas calor = mas obstaculo visto”. Las columnas se ordenan de atras hacia adelante (mayor y primero) para que el painter’s algorithm resuelva oclusiones entre vecinas. 

// Reduccion del cuerpo principal del renderer — drawHeatColumns()
const sorted = heat.slice().sort((a, b) => b[1] - a[1]);

for (const h of sorted) {
    const [gx, gy] = this.worldToScreen(h[0] * cell, h[1] * cell);
    const intensity = Math.pow(h[2] / maxHits, 0.5);
    const colH = COLUMN_HEIGHT_PX * intensity;
    const topY = gy - colH;

    // 1) Sombra en el suelo
    ctx.fillStyle = `rgba(0,0,0,${0.35 * intensity})`;
    ctx.ellipse(gx, gy + cellPxYGround * 0.25, cellPxX * 0.5, cellPxYGround * 0.5, ...);

    // 2) Cara frontal con gradiente vertical
    const grd = ctx.createLinearGradient(gx, topY, gx, gy);
    grd.addColorStop(0, `rgba(${rT},${gT},${bT},${0.45 + intensity * 0.5})`);
    grd.addColorStop(1, `rgba(...)`);
    ctx.fillRect(gx - cellPxX/2, topY, cellPxX, colH + 1);

    // 3) Cara superior (paralelogramo)
    ctx.moveTo(...); ctx.lineTo(...); ctx.closePath(); ctx.fill();

    // 4) Arista superior luminosa
    ctx.strokeStyle = `rgba(255,240,200,${0.25 * intensity})`;
}

2.4 Grilla en Perspectiva y Fondo

Sobre el suelo se dibuja una grilla de 1 m x 1 m con lineas proyectadas una a una a traves de worldToScreen, lo cual respeta la inclinacion. Los ejes X = 0 e Y = 0 se pintan en cian tenue (rgba(90, 168, 255, 0.35)) como referencia de origen. El fondo usa dos gradientes lineales — uno del “cielo” (hasta el 18% superior) y otro del “suelo” — para reforzar sensacion de horizonte sin ser intrusivo.

2.5 Trayectoria, Waypoints y Robot sobre el Terreno

Sobre la proyeccion se superponen:

  • Sombra de la ruta (linea negra gruesa ligeramente desplazada en Y).
  • Linea neon verde con shadowBlur para dar glow.
  • Flechas direccionales cada tramo > 40 px para indicar sentido de recorrido.
  • Waypoints con poste vertical + cabeza coloreada. Origen en verde (etiqueta ORIGEN), intermedios en azul, ultimo en rojo, waypoint activo durante ejecucion en ambar. Cuando hay ≤ 40 waypoints, se pinta el numero centrado dentro de la cabeza.
  • Robot como circulo azul con sombra y flecha de heading (yaw) tambien foreshortened.

Invariante 1. Cualquier mutacion destructiva (add, remove, drag inicial, clear) llama a pushHistory() antes de modificar. Esto garantiza que Deshacer siempre retrocede un paso coherente.
Invariante 2. edit.draggingIdx se pone a -1 en pointerup, pointercancel y en pointerdown si el click no cae sobre un waypoint. No hay rutas donde el estado quede “arrastrando” sin pointer asociado.

4. Robustez del Seguidor de Auto-Ruta

4.1 Diagnostico del Problema Reportado

El operador reporto que al pulsar Iniciar ruta, el robot no recibia la senal. Analisis:

  1. El seguidor dependia de proximity_sensor["_pose_valid"] y entraba en bucle de espera infinito si el sensor no estaba suscrito al lidar.
  2. No habia llamado a BalanceStand previo al primer Move: si el robot estaba sentado o en cualquier estado que no fuera balance stand, el Go2 descartaba los comandos de velocidad silenciosamente.
  3. Los waypoints guardados desde el Control Remoto podian estar en un frame de coordenadas distinto al del pose actual del lidar (especialmente si la ruta se grabo con dead reckoning y la sesion de Auto-Ruta inicia con el sensor recien activado en otra pose inicial).

4.2 Remedio — Flujo Endurecido

async def _autoroute_follow_loop():
    state = autoroute_state
    try:
        # 1) BalanceStand previo: sin esto el Go2 ignora Move.
        emit_log('info', 'Auto-Ruta: pidiendo BalanceStand')
        try:
            await robot_send_command("BalanceStand")
        except Exception as exc:
            emit_log('warning', f'BalanceStand fallo: {exc}')

        # 2) Espera de pose valida con timeout explicito.
        if not await _autoroute_wait_for_pose(5.0):
            emit_log('error', 'Lidar no reporto pose en 5 s. Activa el sensor.')
            state["_cancel"] = True
            return

        # 3) Traslado automatico: el primer waypoint queda bajo el robot.
        pose_x = proximity_sensor["_pose_x"]
        pose_y = proximity_sensor["_pose_y"]
        ox = float(waypoints[0]["x"]) - pose_x
        oy = float(waypoints[0]["y"]) - pose_y
        translated = [
            {"x": float(w["x"]) - ox, "y": float(w["y"]) - oy}
            for w in waypoints
        ]
        state["waypoints"] = translated
        emit_log('info', f'Ruta trasladada (offset {ox:+.2f}, {oy:+.2f})')

        # 4) Loop normal por ciclos y waypoints.
        for cycle in range(1, state["cycles_total"] + 1):
            for i, wp in enumerate(state["waypoints"]):
                await _autoroute_go_to(wp)

4.3 _autoroute_wait_for_pose — Espera con Deadline

async def _autoroute_wait_for_pose(timeout_s=5.0):
    deadline = asyncio.get_running_loop().time() + timeout_s
    while not proximity_sensor["_pose_valid"]:
        if asyncio.get_running_loop().time() > deadline:
            return False
        await asyncio.sleep(0.15)
    return True
Resultado. El loop ya nunca queda pegado esperando una pose que no llega. Si el timeout vence, se emite un error explicito al frontend indicando que el operador debe activar el sensor en el Control Remoto y verificar que el robot publique utlidar/robot_pose.

4.4 Traslado Automatico al Origen del Robot

El primer waypoint guardado se alinea con la pose actual del robot y todos los subsiguientes se trasladan por el mismo offset. Esto es robusto frente a tres escenarios frecuentes:

  • Rutas grabadas con dead-reckoning (sensor apagado durante la grabacion): el frame arranca en (0, 0) relativo al lidar actual tras el traslado.
  • Rutas manuales puestas por click sobre un canvas sin heatmap: el origen del usuario se convierte automaticamente en donde esta el robot.
  • Rutas grabadas en otra sesion: aunque los numeros absolutos hayan derivado, la forma relativa del recorrido se preserva.
Consecuencia conocida. El traslado ignora la diferencia de yaw: si el robot empezo la grabacion mirando al norte y al iniciar Auto-Ruta mira al este, el recorrido se ejecutara rotado 90°. Para el caso de uso actual (laboratorio, rutas cortas) esto es aceptable; si se requiere consistencia absoluta, se puede extender el traslado a affine 2D (traslacion + rotacion) capturando tambien el yaw al momento de guardado.

Recomendaciones de Desarrollo desde este Punto

Linea 1 — Correccion de Yaw en Traslado de Waypoints (prioridad alta)

Extender el traslado actual a una transformacion afin 2D completa: guardar tambien el yaw al momento de grabar la ruta (o al colocar el primer waypoint manual) y, al iniciar la Auto-Ruta, aplicar una rotacion igual a yaw_actual - yaw_grabacion sobre el plano. Elimina la dependencia de que el operador inicie el seguidor con el robot orientado igual que al guardar.

Linea 2 — Heatmap Incremental Durante la Ejecucion (prioridad media)

Actualmente la Auto-Ruta renderiza el heatmap estatico que se guardo. Se podria re-suscribir al canal lidar_points durante el seguimiento para enriquecer el mapa en vivo, mostrando al operador obstaculos nuevos que no estaban cuando se grabo la ruta. Caso de uso claro: ambientes dinamicos (personas, muebles que se movieron).

Linea 3 — Tests Unitarios de la Proyeccion (prioridad media)

El par worldToScreen / screenToWorld debe ser inverso exacto para que el click-para-waypoint caiga donde el usuario espera. Hoy se valida solo visualmente. Se sugiere un test de propiedad: para una muestra aleatoria de puntos mundo, aplicar ida y vuelta y verificar que el error es < 1e-6. Idem para puntos pantalla.

Linea 4 — Indicador Visible de “Pose Lista” en Auto-Ruta (prioridad baja)

El boton Iniciar ruta hoy solo se deshabilita si faltan waypoints, pero no si falta pose del lidar. Agregar un pill en el encabezado (“Pose OK” verde / “Sin pose” gris) leido del mismo stream lidar_points evita que el operador pulse Iniciar cuando el sensor aun no esta listo, ahorrando los 5 s de timeout.

Linea 5 — Soporte de Multiples Rutas Guardadas (prioridad baja)

La clave daiver:lastRoute solo conserva la ultima ruta. Extender a un listado (daiver:routes[]) con nombre editable permitiria guardar ambientes distintos (p. ej. “laboratorio”, “pasillo”, “recorrido demo”) y cambiar entre ellos sin volver a caminar.

Consideraciones Transversales

Seguridad operativa. El Force Mode transfiere explicitamente la responsabilidad del bypass del sensor al operador. Es importante conservar el badge FORCE visible para que nunca haya confusion sobre si la proteccion esta activa. La boton de PARADA (Damp) sigue siendo corte incondicional y debe respetarse en cualquier rutina autonoma.
Rendimiento de renderizado. El redibujado del canvas 2.5D se ejecuta cada 200 ms (setInterval). En mapas muy poblados (>5000 celdas activas) podria requerir o bien downsampling visual (decimar celdas por intensidad antes de dibujar) o bien migrar a OffscreenCanvas + requestAnimationFrame con budget de frame.
Documentacion para el operador. Se recomienda actualizar el README del proyecto con la tabla de comportamientos resultantes (seccion 1.7) y capturas de pantalla de los tres componentes nuevos: badge FORCE, boton Override movil y toolbar del editor de Auto-Ruta.
