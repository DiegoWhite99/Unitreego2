C. Integracion de YOLO v8

C.1 Arquitectura del Detector

El modulo yolo_detector.py implementa un pipeline de inferencia desacoplado en tres componentes independientes que se comunican mediante una cola thread-safe (queue.Queue) con descarte de frames antiguos (backpressure). Esto desacopla la tasa de llegada de frames (30 fps del Go2) de la tasa de inferencia del modelo, evitando bloqueos en el hilo asyncio que maneja WebRTC.

CAPA 1 — FUENTE DE FRAMES
SOURCE_ROBOT: callback WebRTC aiortc, push_frame(bgr)
SOURCE_WEBCAM: hilo con cv2.VideoCapture (fallback, camara local)
[ encola en Queue(maxsize=2) ]
CAPA 2 — COLA CON DESCARTE
Si la cola esta llena, se descarta el frame mas antiguo antes de encolar el nuevo.
Politica: priorizar latencia baja sobre completitud.
[ consumido por hilo dedicado ]
CAPA 3 — HILO DE INFERENCIA
_inference_loop(): model.predict() con umbral de confianza (conf=0.35),
anotacion con r.plot(), medicion de FPS por ventana de 1 s.
[ publica en estado compartido bajo lock ]
CAPA 4 — SALIDA
_latest_frame_jpeg → stream MJPEG (multipart/x-mixed-replace)
_latest_detections → JSON con candidatos a waypoint

C.2 Formato de las Detecciones (Candidato a Waypoint)

Cada deteccion no solo reporta la clase y la caja delimitadora: el detector agrega metadatos derivados que son directamente consumibles por una politica de navegacion. Este es el puente explicito entre percepcion (vision) y accion (movimiento). 

{
    "label": "person",                # Clase detectada por YOLO
    "confidence": 0.847,              # Confianza [0, 1]
    "bbox": [312.4, 98.1, 501.7, 402.3],
    "center": [407.0, 250.2],          # Centroide en pixeles
    "norm_center": [0.636, 0.521],     # Normalizado [0, 1] (independiente de resolucion)
    "area_ratio": 0.163,              # Fraccion del frame ocupada (proxy de distancia)
    "direction": "right",             # left | center | right (umbrales 0.35 / 0.65)
    "distance_hint": "mid"            # near (>0.25) | mid (>0.08) | far
}
Decision de diseno. Los campos direction y distance_hint son buckets discretos en vez de valores continuos. Esto simplifica el mapeo a comandos de movimiento (p. ej. direction="left" + distance_hint="far" → giro a la izquierda + avance) y da robustez frente al ruido de deteccion cuadro a cuadro.

C.4 Enganche con el Canal de Video WebRTC del Go2

Durante robot_connect(), se registra un callback sobre la pista de video entregada por aiortc y se activa explicitamente el canal de video del Go2. La desconexion apaga el canal y detiene el detector si la fuente activa era el robot. 

async def _go2_video_callback(track):
    """Lee frames del Go2 y los pasa al detector YOLO."""
    while True:
        frame = await track.recv()
        bgr = frame.to_ndarray(format="bgr24")
        yolo_detector.push_frame(bgr)

# En robot_connect():
robot_connection.video.add_track_callback(_go2_video_callback)
robot_connection.video.switchVideoChannel(True)

# En robot_disconnect():
if yolo_detector.is_running() and yolo_detector.status()["source"] == "robot":
    yolo_detector.stop()
robot_connection.video.switchVideoChannel(False)

D. SDK de Navegacion Go2

El SDK de navegacion del Go2 en este proyecto no es una libreria externa sino un conjunto de primitivas de movimiento construidas sobre el canal rt/api/sport/request de la conexion WebRTC. Esta actualizacion consolida esas primitivas y agrega el enganche de vision que las convierte en base para navegacion reactiva.

D.1 Primitivas de Movimiento

PrimitivaFirmaProposito
robot_mover async (x, y, z, duracion) Publica comandos api_id=1008 cada 200 ms durante duracion segundos. Requerido porque el Go2 descarta velocidades si no se reiteran.
publish_request_new async (topic, payload) Envia un comando SPORT_CMD puntual (BalanceStand, SitDown, Damp, etc.)
stop_routine_flag Flag global Bandera de interrupcion cooperativa usada por todas las rutinas y por robot_mover para aborto seguro.

D.2 Modelo de Ejecucion

Hilo asyncio   → event_loop dedicado:
                    - robot_connect / robot_disconnect
                    - robot_mover (movimiento continuo a 5 Hz)
                    - rutinas autonomas (patrol, jump, explore)

Recomendaciones de Desarrollo desde este Punto

A partir del estado actual, se identifican cinco lineas de trabajo ordenadas por prioridad tecnica y valor para el proyecto. Las primeras dos son requisitos para cerrar el ciclo percepcion-accion; las tres restantes amplian el alcance.

Linea 1 — Controlador Vision-Navegacion (prioridad alta)

Construir el componente que falta para cerrar el lazo: un modulo go2_navegation.py que consuma el estado del detector y publique comandos de movimiento. Implementacion sugerida:

  • Hilo o asyncio.Task que lee yolo_detector.get_detections() a 5–10 Hz.
  • Maquina de estados: IDLE, SEARCHING, APPROACHING, ARRIVED, ABORT.
  • Selector de objetivo (por clase, p. ej. “person” o “sports ball”) configurable desde la UI.
  • Politica de control proporcional sobre norm_center[0] para giro y area_ratio para avance.
  • Detener ante perdida de deteccion durante mas de N frames consecutivos.
  • Nuevos endpoints: POST /api/nav/follow, POST /api/nav/stop, GET /api/nav/status.

Linea 2 — Robustez del Canal WebRTC-YOLO (prioridad alta)

  • Reconexion automatica del callback de video si la pista se cae (actualmente se registra un warning y termina).
  • Metrica de frames descartados por backpressure en /api/yolo/status para medir saturacion.
  • Parametro configurable de resolucion de entrada: hacer downscale antes de model.predict() si la CPU no da el ancho de banda.
  • Soporte opcional de aceleracion GPU (device=0 en Ultralytics) detectable en runtime.

Linea 3 — Rutinas Autonomas Guiadas por Vision (prioridad media)

Reescribir las tres rutinas existentes (Patrullaje, Salto, Exploracion) para que consulten las detecciones y se detengan o desvien ante obstaculos. Ejemplos:

  • Patrullaje con evasion: interrumpir el avance si direction="center" y distance="near".
  • Exploracion con memoria: registrar clases detectadas por tramo para generar un reporte al finalizar.
  • Rutina de seguimiento: nueva rutina dedicada que use el controlador de la Linea 1.

Linea 4 — Persistencia y Telemetria (prioridad media)

  • Grabacion opcional del stream MJPEG en disco (cv2.VideoWriter) con timestamps.
  • Log estructurado (JSON Lines) de las detecciones para analisis posterior o entrenamiento.
  • Dashboard de telemetria historica: bateria, FPS promedio, comandos enviados por minuto.
  • Exportacion de sesion como paquete reproducible (video + CSV de detecciones + log de comandos).

Linea 5 — Modelo y Dominio (prioridad baja)

  • Evaluar yolov8s.pt o yolov8m.pt si la CPU lo soporta: mejor precision para objetos pequenos.
  • Fine-tuning sobre un dataset propio del laboratorio para clases relevantes al caso de uso (p. ej. obstaculos especificos de la CUN).
  • Agregar segunda pasada con clasificador de pose (YOLO-Pose) para interaccion humano-robot.
  • Explorar estimacion de profundidad monocular (MiDaS, Depth-Anything) para mejorar distance_hint.

Consideraciones Transversales

Seguridad operativa: cualquier modulo que mueva el robot de forma autonoma debe respetar la bandera stop_routine_flag y verificarla entre cada publicacion de comando. El boton de emergencia (Damp) debe mantenerse como corte incondicional.
Testing: la Linea 1 y 2 son candidatas naturales a cobertura de tests. Se recomienda extender [tests/test_integracion.py](tests/test_integracion.py) con casos que simulen detecciones sinteticas mediante yolo_detector.push_frame() con imagenes de referencia.
Documentacion: a medida que el SDK de navegacion gane modulos (controlador, rutinas guiadas), conviene extraerlo a un paquete go2_navegation/ con su propio __init__.py para mantener app.py como capa de transporte HTTP/WebSocket delgada.

1. Descripcion General del Proyecto

Daiver Control CUN es una aplicacion web completa para el control remoto del robot cuadrupedo Unitree Go2 Air a traves del protocolo WebRTC. El sistema permite a los usuarios interactuar con el robot desde cualquier navegador web moderno, proporcionando control de movimiento en tiempo real, ejecucion de poses y trucos, y rutinas autonomas preprogramadas.

El proyecto ofrece dos interfaces diferenciadas:

Interfaz URL Usuarios Objetivo Caracteristicas Principales
Dashboard / Operadores tecnicos Control preciso de movimiento, telemetria, logs en tiempo real
Landing (Daiver) /landing Publico general Interfaz amigable, sintesis de voz, botones de acciones con feedback

2. Arquitectura del Sistema

El sistema sigue una arquitectura cliente-servidor con comunicacion bidireccional en tiempo real:

NAVEGADOR WEB (Chrome / Edge / Firefox)
Dashboard (index.html)  |  Landing Page (landing.html)
↓ HTTP + Socket.IO ↓
SERVIDOR FLASK (app.py — Puerto 5000)
API REST + Socket.IO + Archivos Estaticos
↓ WebRTC (aiortc) ↓
UNITREE Go2 AIR (IP: 192.168.1.36)
Sport Mode Commands via WebRTC PubSub

2.1 Flujo de Comunicacion

  1. El usuario interactua con la interfaz web (botones, teclado, D-Pad).
  2. Las acciones se envian al servidor Flask mediante HTTP REST (acciones puntuales) o Socket.IO (movimiento continuo).
  3. El servidor Flask traduce las peticiones a comandos SPORT_CMD del robot.
  4. Los comandos se envian al Go2 Air via WebRTC usando la libreria unitree_webrtc_connect.
  5. El robot ejecuta el comando y el servidor actualiza el estado global.
  6. El estado actualizado se propaga a todos los clientes conectados via Socket.IO.

2.2 Modelo de Concurrencia

El servidor utiliza un hilo dedicado con un event loop asyncio para las operaciones WebRTC, separado del hilo principal de Flask. Esto permite que las rutinas autonomas (que pueden durar varios minutos) se ejecuten sin bloquear las peticiones HTTP del servidor. 

# Modelo de hilos
Hilo Principal  → Flask + Socket.IO (peticiones HTTP, eventos WebSocket)
Hilo Asyncio   → Event loop dedicado (WebRTC, rutinas autonomas, movimiento)

4.4 Funcion de Movimiento

El robot Unitree Go2 requiere comandos de movimiento continuos (cada 200ms) para mantener el desplazamiento. Un solo comando no genera movimiento sostenido. 

async def robot_mover(x, y, z, duracion):
    """Envia comandos de movimiento cada 0.2s durante la duracion indicada."""
    pasos = int(duracion / 0.2)
    for _ in range(pasos):
        if stop_routine_flag:
            break
        robot_pub_sub.publish("rt/api/sport/request", {
            "header": {"identity": {"api_id": 1008}},
            "parameter": json.dumps({"x": x, "y": y, "z": z})
        })
        await asyncio.sleep(0.2)

8. Rutinas Autonomas

8.1 Patrullaje (Patrol)

Recorrido en zigzag de 8 pasos que cubre un area rectangular:

  1. Avanzar 5.5 metros hacia adelante
  2. Girar 180 grados
  3. Avanzar 5 metros
  4. Girar 180 grados
  5. Avanzar 3.75 metros
  6. Girar 180 grados
  7. Avanzar 4.8 metros (retorno)
  8. Girar 180 grados (posicion original)

8.2 Salto (Jump)

Secuencia de 11 pasos combinando avance y saltos:

  1. BalanceStand (estabilizar)
  2. Avanzar 2 metros
  3. FrontJump
  4. BalanceStand
  5. Avanzar 2 metros
  6. FrontJump
  7. BalanceStand
  8. Girar 180 grados
  9. Avanzar 4 metros (retorno)
  10. FrontJump final
  11. BalanceStand

8.3 Exploracion (Explore)

Recorrido perimetral en forma de cuadrado:

  1. Avanzar 3 metros → Girar 90 grados derecha
  2. Avanzar 3 metros → Girar 90 grados derecha
  3. Avanzar 3 metros → Girar 90 grados derecha
  4. Avanzar 3 metros → Girar 90 grados derecha (retorno)
Importante: Todas las rutinas verifican la bandera stop_routine_flag entre cada paso. Si se presiona el boton de parada de emergencia, la rutina se interrumpe inmediatamente de forma segura.

10. Guia de Uso de la Aplicacion

10.1 Controlar Movimiento (Dashboard)

  1. Asegurar que el robot esta conectado (indicador verde).
  2. Con D-Pad: Hacer clic o mantener presionados los botones direccionales.
  3. Con Teclado: Usar las teclas WASD para moverse, Q/E para girar, Espacio para detener.
  4. Velocidad: Ajustar el slider de velocidad (10% - 100%).
  5. Parar: Hacer clic en STOP o presionar Espacio.

10.2 Ejecutar Acciones

  1. Navegar a la seccion de "Acciones" o "Trucos".
  2. Hacer clic en el boton deseado (Saludar, Bailar, Saltar, etc.).
  3. El robot ejecutara la accion y el log mostrara el resultado.

10.3 Iniciar una Rutina

  1. Asegurar que el area esta despejada (el robot se movera de forma autonoma).
  2. Seleccionar la rutina deseada (Patrullaje, Salto o Exploracion).
  3. Monitorear el progreso en los logs en tiempo real.
  4. Para detener la rutina: presionar "Detener Rutina" o el boton de emergencia.

10.4 Usar el Landing Page (Daiver)

  1. Acceder a http://localhost:5000/landing.
  2. El sistema de voz se inicializa automaticamente.
  3. Probar las frases rapidas para escuchar a Daiver hablar.
  4. Ejecutar acciones con los botones (cada accion incluye voz).
  5. Ajustar la velocidad de la voz con el control deslizante.

10.5 Parada de Emergencia

IMPORTANTE: En cualquier momento, presionar el boton rojo de EMERGENCIA detendra inmediatamente el robot enviando el comando Damp. Este comando desactiva los motores de forma suave. La parada de emergencia funciona incluso durante la ejecucion de rutinas.

La voz no funciona Navegador sin soporte Speech API Usar Chrome o Edge. Verificar permisos de audio
Socket.IO no conecta Puerto 5000 bloqueado Verificar firewall y que el servidor esta corriendo
